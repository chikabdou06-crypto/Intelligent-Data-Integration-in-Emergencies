1. The Request Lifecycle — End-to-End Data Flow

Every user query passes through three sequential phases. The entire cycle happens inside a single HTTP request:

User prompt (string)
        │
        ▼
┌───────────────────────────────────────────┐
│  PHASE 1 — PLANNER  (planner.py)          │
│  ① discover_skills() → keyword match      │
│  ② Build tool menu from registry           │
│  ③ Execute VaultCatalogTool (catalog)      │
│  ④ Assemble system prompt                  │
│  ⑤ LLM call → JSON execution plan         │
└───────────────────────────────────────────┘
        │  list[dict] — 1 to 6 steps
        ▼
┌───────────────────────────────────────────┐
│  PHASE 2 — ORCHESTRATOR  (orchestrator.py)│
│  For each step:                            │
│    ① Resolve $PREV/$STEP_N placeholders    │
│    ② Check SQLite cache (SHA-256 hash)     │
│    ③ If not cached → tool.execute(**args)  │
│    ④ Store result in cache                 │
│    ⑤ Append to executed[] list             │
└───────────────────────────────────────────┘
        │  list[dict] — executed plan with results
        ▼
┌───────────────────────────────────────────┐
│  PHASE 3 — SYNTHESIZER  (synthesis.py)    │
│  ① Build synthesis prompt (date + prompt   │
│    + full execution trace as JSON)         │
│  ② LLM call → Markdown report             │
│  ③ Strip <thinking> blocks                │
└───────────────────────────────────────────┘
        │  string — final markdown response
        ▼
JSON response to client
Design Principle: The pipeline is strictly linear — no loops, no re-planning, no self-correction. The Planner reasons once, the Orchestrator executes deterministically, and the Synthesizer narrates. This makes the system predictable, debuggable, and easy to trace through logs.

2. The Entry Point — app.py

The FastAPI application defines a single core endpoint that triggers the full agent cycle.

backend/app.py
async def chat(request: Request) → JSONResponse

This is the main HTTP handler, decorated as @app.post("/api/chat"). It receives a JSON payload with a message field (the user's prompt) and orchestrates the three phases.

Internal flow:

  1. Payload extraction: Parses the raw HTTP body with await request.json(). If the JSON is invalid or the message field is empty, it returns a 400 error immediately.
  2. Synchronous agent wrapper: Because the core pipeline uses blocking I/O (HTTP requests to external APIs, SQLite calls, LLM calls), it defines an inner function run_agent_sync() and delegates it to FastAPI's run_in_threadpool(). This prevents the synchronous pipeline from blocking the async event loop.
  3. Three-phase execution:
def run_agent_sync():
    # Phase 1 — Plan
    steps = generate_plan(prompt)         # → list[dict]

    # Phase 2 — Execute
    executed_plan = execute_plan(steps)   # → list[dict] with results

    # Phase 3 — Synthesize
    reply = generate_synthesis(prompt, executed_plan)  # → str

    return steps, executed_plan, reply

Response structure:

The endpoint assembles a response that contains not just the final reply, but the entire execution trace for transparency:

{
    "reply":        "... markdown report ...",
    "tool_used":    "aemet_forecast",           // primary tool (or "multi_tool")
    "tools_used":   ["aemet_forecast", "csv_reader"],  // all tools
    "plan":         [ ... ],                    // raw plan from Planner
    "tool_results": [ ... ],                    // full executed plan
    "tool_data":    { ... }                     // last tool's raw result
}
Why expose the full trace? The frontend uses tool_results to render the Data Results panel and the Tool Status indicators. It also allows debugging — you can see exactly what the Planner decided, what arguments were resolved, and what each tool returned.

3. Phase 1: The Planner — planner.py

The Planner is the most complex module. It transforms a raw user prompt into a structured, executable plan. It involves four distinct operations: skill discovery, skill selection, tool menu construction, and LLM plan generation.

3.1 — generate_plan(prompt)

backend/core/planner.py · Lines 88–171
def generate_plan(prompt: str) → list[dict]

This is the top-level entry point for Phase 1. It returns a list of step dictionaries, each containing a tool name and an arguments dict.

Step-by-step internal logic:

① Skill Routing (no LLM call):

all_skills = discover_skills()                    # scan backend/skills/*.md
selected_skills = select_relevant_skills(prompt, all_skills)  # keyword match

If skills match, it assembles a skills_section string by concatenating the full Markdown body of each matched skill, wrapped with headers. If no skills match, this section is an empty string.

② Tool Menu Construction:

tools = list_all_tools()   # returns list of tool names from static registry

for tool_name in tools:
    tool_instance = get_tool(tool_name)    # lazy import + instantiate
    schema = tool_instance.get_schema()    # introspect execute() type hints
    # Build a line like:
    # - "csv_reader": Reads CSV files. Arguments: {filename: <string required>, ...}

For each registered tool, it imports the class, generates its JSON schema (via BaseTool.get_schema()), and formats it into a human-readable menu line. This menu is what the LLM sees as its "toolbox".

③ Vault Catalog Injection:

catalog_tool = VaultCatalogTool()
raw_catalog = catalog_tool.execute()     # scans CSVs, PDFs, Drive, Neo4j
catalog_str = json.dumps(raw_catalog, indent=2)

The Planner physically executes the VaultCatalogTool to discover what data sources exist. This JSON blob is injected into the system prompt so the LLM knows which CSV filenames, PDF documents, and Google Drive files are available to query.

④ LLM Call:

system_msg = get_planner_prompt(catalog_str, skills_section, tools_text)
llm = LLMClient(role="planner", temperature=0.1)
result = llm.generate_json(system_msg + f'\n\nUser Prompt: "{prompt}"\nJSON Response:')

The assembled prompt (catalog + skills + tool menu + user query) is sent to the LLM. The generate_json() method handles parsing the response: it strips <thinking> blocks, looks for JSON inside markdown fences, and falls back to finding the first { or [ character.

⑤ Plan Extraction and Capping:

steps = result.get("steps", [])
if not steps:
    steps = [{"tool": "general", "arguments": {}}]   # fallback
return steps[:6]   # hard cap at 6 steps

If the LLM returns an empty or malformed plan, the function defaults to a single general step (which makes the Synthesizer handle the query as free-form conversation). A hard cap of 6 steps prevents runaway plans.

3.2 — discover_skills()

backend/core/planner.py · Lines 34–57
def discover_skills() → list[dict]

Scans the backend/skills/ directory for all .md files and returns a list of skill metadata dictionaries.

for skill_path in sorted(SKILLS_DIR.glob("*.md")):
    raw = skill_path.read_text(encoding="utf-8")

Each .md file uses YAML frontmatter with name and description fields. The function reads the entire file but separates the frontmatter from the body — this is important because only the body will be injected into the LLM context later, and only for matched skills.

3.3 — _parse_skill_frontmatter(raw)

backend/core/planner.py · Lines 11–31
def _parse_skill_frontmatter(raw: str) → tuple[str, str, str]

A lightweight YAML parser (does not use the yaml library — intentionally avoids the dependency). Looks for lines starting with name: and description: between the two --- delimiters. Returns (name, description, body) where body is everything after the closing ---.

if raw.startswith("---"):
    end = raw.find("---", 3)           # find closing ---
    frontmatter = raw[3:end]
    body = raw[end + 3:].strip()
    for line in frontmatter.splitlines():
        if line.startswith("name:"):
            name = line[5:].strip()
        elif line.startswith("description:"):
            description = line[12:].strip()

3.4 — select_relevant_skills(prompt, all_skills)

backend/core/planner.py · Lines 60–85
def select_relevant_skills(prompt: str, all_skills: list) → list[dict]

Performs keyword matching between the user prompt and each skill's description. The matching works as follows:

prompt_lower = prompt.lower()

for skill in all_skills:
    # Tokenize the description into words > 3 characters
    keywords = [w.lower() for w in re.findall(r'\b\w+\b', skill["description"]) if len(w) > 3]

    # Check if ANY keyword appears in the user prompt
    matched = any(kw in prompt_lower for kw in keywords)

    if matched:
        selected.append(skill)

The function extracts words longer than 3 characters from the skill's description field and checks if any of those words appear as substrings in the user's prompt. This is a deliberately simple heuristic — no embeddings, no LLM call — because it runs on every request and needs to be fast.

Trade-off: This approach is fast (pure string matching, O(n·k)) but imprecise. A skill about "earthquake emergency protocols" would match any prompt containing "earthquake" or "protocols" but would miss semantically similar queries like "seismic activity response guidelines". A future improvement could use embedding similarity with a threshold.

4. Phase 2: The Orchestrator — orchestrator.py

The Orchestrator is a deterministic execution engine. It receives the JSON plan from the Planner and runs each step in sequence, resolving dependencies between steps and managing the execution cache.

4.1 — execute_plan(steps)

backend/core/orchestrator.py · Lines 64–123
def execute_plan(steps: list) → list[dict]

The main loop. Takes a list of plan steps and produces a list of executed steps, each annotated with its result.

executed = []

for step in steps:
    tool_name = step.get("tool", "general")
    args = step.get("arguments", {})

    # ① Resolve cross-step dependencies
    resolved_args = _enrich_args_from_prior(args, executed)

    # ② Skip "general" tool (just a no-op placeholder)
    if tool_name == "general":
        executed.append({"tool": tool_name, "arguments": resolved_args, "result": None})
        continue

    # ③ Instantiate tool via lazy registry
    tool_instance = get_tool(tool_name)

    # ④ Check cache
    if getattr(tool_instance, "cacheable", True):
        cached = get_cached_result(tool_name, resolved_args)
        if cached is not None:
            executed.append({..., "result": cached, "cached": True})
            continue

    # ⑤ Execute the tool
    result = tool_instance.execute(**resolved_args)

    # ⑥ Cache successful results
    if result.get("status") != "error":
        set_cached_result(tool_name, resolved_args, result)

    executed.append({"tool": tool_name, "arguments": resolved_args, "result": result})

Each entry in the output executed list contains:

KeyTypeMeaning
toolstrTool name (e.g. "csv_reader")
argumentsdictThe resolved arguments (after placeholder substitution)
resultdict | strThe raw output from tool.execute(), or None for general
cachedboolIf True, the result was served from cache without executing the tool
errorboolIf True, the tool threw an exception

4.2 — _resolve_placeholder(value, prior)

backend/core/orchestrator.py · Lines 20–53
def _resolve_placeholder(value, prior: list) → any

Resolves a single placeholder string like $PREV.data.0.postal into the actual value from a prior step's result. This is the mechanism that allows the Planner to chain tool outputs.

Two resolution modes:

$PREV.path — Smart backwards search:

if token.startswith("PREV."):
    path = token[5:]               # e.g. "data.0.postal"
    # Search ALL prior steps from most recent to oldest
    for step_idx in range(len(prior) - 1, -1, -1):
        source = prior[step_idx].get("result") or {}
        val = _deep_get(source, path)
        if val is not None:
            return val

$PREV does NOT simply look at the immediately prior step — it scans backwards through all executed steps until it finds a result that contains the requested path. This handles cases where step N-1 might fail but step N-2 has the needed data.

$STEP_N.path — Explicit index reference:

if token.startswith("STEP_"):
    idx = int(rest.partition(".")[0])    # e.g. STEP_0 → idx=0
    source = prior[idx].get("result")
    return _deep_get(source, path)

Allows the Planner to reference a specific step by its 0-based index, rather than relying on backward search.

4.3 — _deep_get(obj, path)

backend/core/orchestrator.py · Lines 4–18
def _deep_get(obj, path: str) → any

A generic path navigator for nested Python data structures. Splits the path by . and traverses dicts and lists accordingly.

for part in path.split("."):
    if isinstance(obj, list):
        obj = obj[int(part)]        # numeric index for arrays
    elif isinstance(obj, dict):
        obj = obj.get(part)         # key lookup for dicts

For example, given the path data.0.municipio and this object:

{
    "data": [
        {"municipio": "Valencia", "magnitud": "3.2"},
        {"municipio": "Alicante", "magnitud": "2.8"}
    ]
}

It navigates: obj["data"] → obj[0] → obj["municipio"] → "Valencia".

4.4 — _enrich_args_from_prior(arguments, prior)

backend/core/orchestrator.py · Lines 55–62
def _enrich_args_from_prior(arguments: dict, prior: list) → dict

Iterates over every key-value pair in the step's arguments dict. For each value that starts with $, it calls _resolve_placeholder() to substitute the actual runtime value. Non-placeholder values are left untouched.

args = dict(arguments or {})
for key, val in list(args.items()):
    resolved = _resolve_placeholder(val, prior)
    if resolved is not None and resolved != val:
        args[key] = str(resolved) if not isinstance(resolved, str) else resolved
return args
Important detail: All resolved values are cast to str unless they are already strings. This is because tool parameters are always passed as keyword arguments to execute(**kwargs), and most tool methods expect string inputs. This prevents type errors when a numeric value extracted from a prior step (e.g., a latitude 38.345) is passed to a tool expecting lat: str.

5. Phase 3: The Synthesizer — synthesis.py

backend/core/synthesis.py · Lines 7–24
def generate_synthesis(prompt: str, executed_plan: list) → str

The final stage. Takes the original user prompt and the complete execution trace (with all tool results) and produces a human-readable Markdown report.

def generate_synthesis(prompt, executed_plan):
    current_date = datetime.now().strftime("%Y-%m-%d %H:%M")
    executed_plan_json = json.dumps(executed_plan, indent=2)

    # Build the synthesis prompt template
    synthesis_prompt = get_synthesis_prompt(current_date, prompt, executed_plan_json)

    # Call LLM with slightly higher temperature for natural prose
    llm = LLMClient(role="synthesizer", temperature=0.3)
    reply = llm.generate(synthesis_prompt).strip()

    # Remove <thinking> blocks if the model generated any
    reply = re.sub(r'<thinking>.*?</thinking>\s*', '', reply, flags=re.DOTALL)

    return reply.strip()

Key design decisions:

  • Full trace injection: The entire executed_plan list is serialized as JSON and embedded in the prompt. This means the Synthesizer sees every tool name, every argument, every result, and every error. It can cross-reference multiple data sources.
  • Date injection: The current timestamp is injected so the LLM can correctly interpret temporal data (e.g., "is this earthquake recent?") without hallucinating the current date.
  • temperature=0.3: Higher than the Planner's 0.1 because the Synthesizer generates prose, not structured JSON. A slight creative boost improves readability without risking factual drift.
  • <thinking> stripping: The prompt instructs the LLM to reason in a <thinking> block before generating its final report. This block is stripped from the output so the user only sees the clean report.

6. The Prompt Templates — prompts.py

This module contains the two system prompts that drive the entire agent's behavior. Both are Python f-strings that receive dynamic data at runtime.

6.1 — get_planner_prompt(catalog_str, skills_section, tools_text)

backend/core/prompts.py · Lines 3–39
def get_planner_prompt(catalog_str, skills_section, tools_text) → str

Assembles the Planner system prompt from three dynamic blocks:

ParameterSourceContent
catalog_strVaultCatalogTool.execute()JSON blob listing all available data — CSV filenames + columns, PDF metadata, Google Drive files
skills_sectionselect_relevant_skills()Full Markdown bodies of matched skills, or empty string if no skills matched
tools_textRegistry iteration in generate_plan()One-line schema for each tool: name, description, parameters with types and required/optional

The prompt contains several mandatory rules that constrain the LLM's behavior:

  • Rule 1 — Cross-step dependencies: Teaches the LLM the $PREV.path placeholder syntax and forbids bracket notation
  • Rule 2 — Sorting: Instructs the LLM to use csv_reader with order_by instead of csv_aggregate for finding max/min rows
  • Rule 3 — Step limit: Max 6 steps; use only as many as needed
  • Rule 4 — Chain of Thought: Forces a <thinking> block before the JSON output
  • Rule 5 — Chitchat: Greetings and casual conversation must produce a single general step with empty arguments
  • Rule 6 — Output format: JSON must be wrapped in a markdown code block

The prompt also contains domain specializations:

  • Seismic querying: Directs the LLM to use the local CSV file pelsiscav_clean_seismic_catalog.csv for historical data, and the siscova_earthquakes API tool for live data
  • Google Drive RAG: Instructs the LLM to look up filenames in the vault catalog and pass them as string arguments to drive_read_sheet, explicitly forbidding $PREV for Drive file names

6.2 — get_synthesis_prompt(current_date, prompt, executed_plan_json)

backend/core/prompts.py · Lines 42–66
def get_synthesis_prompt(current_date, prompt, executed_plan_json) → str

Builds the Synthesizer prompt. It receives:

  • current_date — a formatted timestamp so the LLM doesn't flag current-year data as "future"
  • prompt — the original user question
  • executed_plan_json — the full execution trace serialized as JSON

The prompt instructs the Synthesizer to perform four specific analytical tasks:

  1. Cross-Source Analysis: Connect data from all tools into a unified narrative
  2. Multi-Input Reasoning: Identify relationships and validation rules across sources
  3. Resolve Discrepancies: If two tools return conflicting data, resolve it logically
  4. Structured Explanation: Present the final answer as a polished Markdown report

7. The Tool Abstraction — base_tool.py & registry.py

Every tool in the system follows a strict contract defined by two components: an abstract base class and a lazy registry.

7.1 — BaseTool (Abstract Base Class)

backend/core/base_tool.py · Lines 5–62
class BaseTool(ABC)

Defines the interface that every tool must implement. Has four class-level attributes and two methods:

AttributeTypeDefaultPurpose
namestr"BaseTool"Unique tool identifier (must match registry key)
descriptionstr"Base description"Human-readable description shown to the Planner LLM
categorystr"general"Grouping category (DATA, API, ANALYSIS, DISCOVERY)
cacheableboolTrueWhether the Orchestrator should cache results for this tool

execute(**kwargs) — Abstract method

Every subclass must implement this method. It receives keyword arguments (the resolved arguments from the plan step) and must return a result — typically a dict with a "status" key.

get_schema() — Automatic schema generation

This classmethod uses Python's inspect.signature() to introspect the execute() method's parameters and type annotations at runtime:

@classmethod
def get_schema(cls):
    sig = inspect.signature(cls.execute)    # inspect the execute method

    for name, param in sig.parameters.items():
        if name == "self": continue

        # Map Python types to JSON schema types
        if   param.annotation == int:   param_type = "integer"
        elif param.annotation == bool:  param_type = "boolean"
        elif param.annotation == float: param_type = "number"
        elif param.annotation == list:  param_type = "array"
        else:                          param_type = "string"

        properties[name] = {"type": param_type}

        # Parameters without defaults are required
        if param.default == inspect.Parameter.empty:
            required.append(name)
Why this matters: When the Planner builds the tool menu, it calls get_schema() on every tool. The schema is rendered as a line in the prompt so the LLM knows exactly what parameters each tool accepts, their types, and which ones are required. This means adding a new tool with typed parameters is automatically reflected in the LLM's knowledge — no prompt editing required.

7.2 — The Lazy Registry (registry.py)

backend/core/registry.py · Lines 1–44

The registry provides three key functions:

@register_tool(name, category) — Decorator

A decorator applied to tool classes. It sets the name and category attributes on the class. Note: this decorator does not add the tool to the runtime registry — that's handled by the static map.

list_all_tools() — List tool names

def list_all_tools():
    return list(_LAZY_REGISTRY.keys())   # instant — no imports needed

Returns all registered tool names from the pre-computed static map. This is O(1) and does not trigger any module imports.

get_tool(tool_name) — Lazy instantiation

def get_tool(tool_name):
    module_path, class_name = _LAZY_REGISTRY[tool_name]
    module = importlib.import_module(module_path)    # import on first use
    tool_class = getattr(module, class_name)
    return tool_class()                                # instantiate

The first time a tool is requested, its module is imported via importlib.import_module(), the class is retrieved by name, and a new instance is created. This is the lazy loading pattern — tools that are never called in a session are never imported.

8. The Execution Cache — cache.py

The cache sits between the Orchestrator and the tools. It prevents redundant API calls by storing and retrieving results in a local SQLite database.

8.1 — Database Schema

CREATE TABLE IF NOT EXISTS tool_cache (
    hash_key   TEXT PRIMARY KEY,
    tool_name  TEXT,
    result     TEXT,               -- JSON-serialized result dict
    timestamp  DATETIME DEFAULT CURRENT_TIMESTAMP
);

The database is stored at backend/vault/cache/execution_cache.sqlite and is auto-created on module import via init_db().

8.2 — _generate_hash(tool_name, kwargs)

backend/core/cache.py · Lines 26–30
def _generate_hash(tool_name: str, kwargs: dict) → str
def _generate_hash(tool_name, kwargs):
    dict_str = json.dumps(kwargs, sort_keys=True)   # deterministic key ordering
    combined = f"{tool_name}::{dict_str}"
    return hashlib.sha256(combined.encode("utf-8")).hexdigest()

The cache key is a SHA-256 hash of the tool name concatenated with the JSON-serialized arguments (with sorted keys for determinism). This means the same tool called with the same arguments will always produce the same hash, regardless of the order the arguments were specified.

8.3 — get_cached_result(tool_name, kwargs)

backend/core/cache.py · Lines 32–41
def get_cached_result(tool_name: str, kwargs: dict) → dict | None

Looks up the hash key in SQLite. If a row exists, the result column (stored as a JSON string) is deserialized and returned. If no cache hit, returns None.

8.4 — set_cached_result(tool_name, kwargs, result)

backend/core/cache.py · Lines 43–57
def set_cached_result(tool_name: str, kwargs: dict, result: any) → None

Serializes the result to JSON and writes it to SQLite using INSERT OR REPLACE — if the hash already exists, the old result is overwritten. If the result is not JSON-serializable (e.g., contains bytes), it falls back to json.dumps(str(result)).

Important behavior: The Orchestrator checks tool_instance.cacheable before cache lookup. Tools like aemet_fire_risk, aemet_warnings, and vision_map_analyzer set cacheable = False because their data is real-time. Additionally, the Orchestrator never caches error results — if result.get("status") == "error", the cache write is skipped.

9.2 — VaultCatalogTool.execute()

backend/tools/local/vault_catalog.py · Lines 15–141
def execute(self) → dict

This tool is unique because the Planner executes it directly during plan generation (not as part of the Orchestrator's loop). It performs five scans:

  1. Local CSVs: Loads csvs_index.json and filters out massive legacy files (CHJ_OpenData, Sismicidad_Historica) to keep the token footprint small
  2. Local PDFs: Loads pdfs_index.json with summaries and chunk counts for each indexed PDF
  3. Local TXT/MD: Walks the vault directory tree (excluding cache/ and catalogs/) for text and markdown files
  4. Neo4j: Attempts a Cypher query to check graph status, labels, and node count (currently disconnected)
  5. Google Drive: Loads the Drive catalog and strips large metadata fields, then queries the Drive API for a quick 5-file preview to verify the connection
Token optimization: The catalog output is deliberately compressed. CSV entries only include filenames and column lists. Google Drive entries are reduced to just name and columns. Legacy CSVs with thousands of columns are excluded entirely. This is critical because this JSON blob is injected into every single Planner prompt — a bloated catalog would waste tokens on every request.

class CsvReaderTool(BaseTool) → execute(filename, filter_column, filter_value, filter_operator, ...)

A rich query engine for CSV files. The execute() method delegates to read_csv_data() which:

  1. Resolves the file path via _resolve_csv_path(filename) — searches vault/csvs/, vault/processed_data/, and backend/data/ (legacy) for the requested filename
  2. Opens and parses the CSV with Python's csv.DictReader
  3. Applies up to two independent filters: Each filter has a column, value, and operator (contains, ==, >, <, >=, <=). Column matching is case-insensitive
  4. Strips geometry columns automatically — removes columns named geometry, geom, wkt, geojson, the_geom, shape to prevent multi-megabyte WKT blobs from inflating the response
  5. Sorts results if order_by is specified — attempts numeric sort first, falls back to string sort
  6. Caps at max_rows (default 500) and flags truncated: true if the cap was hit

The companion CsvAggregateTool provides server-side aggregation (sum, count, avg, min, max) over all rows without the row cap, with optional group_by support.

10.2 — VaultPdfSearchTool (Semantic retrieval)

backend/tools/local/vault_pdf_search.py
class VaultPdfSearchTool(BaseTool) → execute(query, top_k=4)

Performs semantic search over PDF documents using vector embeddings. The execute() method:

  1. Embeds the query using the Google Gemini Embedding API (text-embedding-004 model, 768 dimensions): 
    client = genai.Client(api_key=google_api_key)
response = client.models.embed_content(
    model="text-embedding-004",
    contents=query,
    config={"output_dimensionality": 768}
)
embedding = response.embeddings[0].values    # 768-dim float vector
  2. Queries Pinecone with the embedding vector to find the top-k most similar document chunks: 
    pc = Pinecone(api_key=api_key)
index = pc.Index("tfm-vault")
res = index.query(vector=embedding, top_k=top_k, include_metadata=True, namespace="vault-pdfs")
  3. Formats results — for each match, extracts the text chunk (capped at 2000 chars), the source filename, the chunk index, and the similarity score
This is the "R" in RAG: The PDF search tool is the purest implementation of Retrieval-Augmented Generation in the system. The user's query is embedded, similar document chunks are retrieved from the vector store, and those chunks are passed to the Synthesizer LLM to generate a grounded answer.
