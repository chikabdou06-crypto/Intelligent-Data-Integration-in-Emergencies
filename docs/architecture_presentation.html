Core: Two-Phase Agentic Pipeline

The brain of the agent — plan first, execute, then synthesize

Phase 1 — The Planner (planner.py)

The Planner receives the user's raw prompt and outputs a structured JSON execution plan containing 1 to 6 steps. Each step specifies which tool to call and with what arguments.

How it works technically:

  1. Skill Routing (no LLM call): Scans the backend/skills/ directory, reads only YAML frontmatter from each .md skill file. Keyword-matches the user prompt against skill descriptions. Only the bodies of matched skills are injected into the LLM context.
  2. Tool Menu Construction: Iterates all registered tools via the registry.py and dynamically builds a schema for each tool (name, description, parameters, required fields).
  3. Vault Catalog Injection: Executes the VaultCatalogTool to discover all available data sources (CSVs, PDFs, Google Drive files) and injects this catalog into the prompt so the LLM knows what data exists.
  4. LLM Call: Sends the assembled system prompt (skills + tools + catalog + user query) to the LLM with temperature=0.1 for deterministic planning. The LLM returns a JSON plan with a <thinking> block (Chain-of-Thought) that is stripped before parsing.
Progressive Skill Disclosure: Skills are NOT all loaded at once. Only the frontmatter is read initially (cheap I/O), and full skill bodies are injected only for those that match the user's prompt. This reduces token usage and keeps the LLM context focused.

Phase 2 — The Synthesizer (synthesis.py)

After all tools have executed, the Synthesizer LLM receives the original user prompt plus the complete execution trace (every tool call, its arguments, and its raw output). It produces a final, polished Markdown report with cross-source analysis, discrepancy resolution, and structured conclusions.

  • Uses temperature=0.3 — slightly higher for more natural language generation
  • Strips <thinking> blocks from the output
  • Specializes in seismic data formatting, PELSISCAV guidelines, and Google Drive sourcing citations

Core: The Orchestrator

orchestrator.py — Sequential tool execution with dependency resolution

What It Does

The Orchestrator takes the JSON plan from the Planner and executes each step sequentially, resolving cross-step dependencies, checking the cache, and collecting results for the Synthesizer.

Cross-Step Dependency Resolution (Placeholder System)

The Planner can chain tool outputs together using placeholder variables:

// Example plan with chained dependencies: { "steps": [ { "tool": "aemet_fire_risk", "arguments": { "query_type": "fire_estimated" } }, { "tool": "vision_map_analyzer", "arguments": { "image_url": "$PREV.map_url", ← resolved at runtime "question": "What is the fire risk level in Valencia?" }} ] }

Resolution mechanisms:

  • $PREV.path.to.field — Smart backwards search through all prior step results (most recent first)
  • $STEP_N.path.to.field — Explicit reference to a specific step index (0-based)
  • Deep path navigation: _deep_get() supports dot-separated keys and numeric array indices (e.g., $PREV.data.0.postal)

Execution Loop (per step)

  1. Resolve — Substitute all $PREV / $STEP_N placeholders with actual values from prior results
  2. Instantiate — Lazily import and instantiate the tool class via registry.get_tool()
  3. Cache Check — Look up the SHA-256 hash of tool_name + args in SQLite; skip execution if cached
  4. Execute — Call tool.execute(**resolved_args) and capture the result
  5. Cache Write — Store successful results in SQLite for future identical calls
Important: The Orchestrator does NOT make LLM calls — it is pure deterministic execution. All intelligence lives in the Planner and Synthesizer. This makes the execution layer fast, testable, and completely predictable.

Multi-Provider LLM Client

llm.py + providers/ — Resilient inference with automatic fallback

Provider Priority Chain

gemini-3.5-flash → 2.5-flash → 2.0-flash
Full vision support (image_bytes)
🥈 Hugging Face Inference
Qwen2.5-72B → Llama-3-8B
Text-only (no vision)
🥉 Ollama (Local)
llama3 → qwen2.5:7b
Self-hosted, offline capable

How Fallback Works

  • 3 retry loops across all providers — if every provider fails, wait 1 second and retry the entire chain
  • Each provider itself tries multiple models in order (e.g., Gemini 3.5 → 2.5 → 2.0)
  • Providers self-report is_configured — unconfigured providers are silently skipped
  • Role-based model selection: Planner uses temperature=0.1 (deterministic), Synthesizer uses temperature=0.3 (creative)

The Tool System

BaseTool → @register_tool → Lazy Registry — 25 tools across 3 categories

BaseTool Abstract Class (base_tool.py)

Every tool extends BaseTool and must implement execute(**kwargs). The class provides:

  • Automatic JSON schema generation via get_schema() — inspects the execute() method's type hints using Python's inspect module to build parameter schemas dynamically
  • Metadata attributes: name, description, category, cacheable

Lazy Registry Pattern (registry.py)

Tools are NOT imported at startup. Instead, a static map (_lazy_registry_static.py) maps tool names to (module_path, class_name) tuples. Tools are imported only when first needed via importlib.import_module(). This keeps server startup fast — no heavy imports until a tool is actually invoked.

# Auto-generated static registry map STATIC_TOOL_MAP = { "aemet_fire_risk": ["backend.tools.api.aemet_fire_risk", "AemetFireRiskTool"], "csv_reader": ["backend.tools.local.csv_reader", "CsvReaderTool"], "web_search": ["backend.tools.api.web_search", "WebSearchTool"], // ... 22 more tools }

Key Tools — Technical Deep Dive

How the most important tools work under the hood

AEMET API Tools (8 tools)

All AEMET tools follow a two-step HTTP pattern mandated by AEMET's OpenData REST API:

  1. Request metadata: GET /opendata/api/... → returns a JSON with a datos URL
  2. Fetch actual data: GET {datos_url} → returns the real payload (JSON, image, or tar archive)

Fire risk maps return PNG images, warnings return CAP 1.2 XML in tar archives, and forecasts return structured JSON.

Warning Tool Detail: aemet_warnings downloads a .tar archive, extracts .xml files, and parses them using Python's xml.etree.ElementTree with the CAP 1.2 namespace (urn:oasis:names:tc:emergency:cap:1.2). It extracts event, severity, urgency, certainty, onset, expiry, color levels, and affected areas.

SISCOVA Earthquakes (siscova_api.py)

Fetches live seismic data from the Valencian Community's official WFS (Web Feature Service) endpoint as CSV. Parses with Python's csv.DictReader, filters future-dated test entries, and sorts by date/time (newest first).

PATRICOVA Flood Risk (patricova_flood.py)

Uses the ArcGIS REST API Identify endpoint to perform server-side spatial intersection. If only a location name is provided (not coordinates), it first geocodes the name via the Nominatim (OpenStreetMap) API, then queries the official flood zone layers.

Vision Map Analyzer (vision_map_analyzer.py)

A multimodal tool that: (1) Downloads image bytes from a URL, (2) Validates the MIME type is image/*, (3) Sends the bytes + a geospatial analysis prompt to Gemini Vision to "read" the map. Explicitly sets cacheable = False since maps change in real-time.

CSV Reader (csv_reader.py)

A rich data query engine with: dual filter support (two independent column filters with operators contains, ==, >, <, >=, <=), sorting (order_by + order_desc), column exclusion, geometry column auto-stripping, and server-side aggregation (sum, count, avg, min, max with optional group_by).

Google Drive Security — Sandbox Model

The agent restricts Google Drive access to a single authorized folder (GOOGLE_DRIVE_FOLDER_ID). Before reading any file, is_file_authorized() traces the file's parent chain up to 5 levels deep to verify it resides inside the sandbox. This prevents prompt-injection attacks from tricking the agent into reading arbitrary files.

Caching & Performance

How the system avoids redundant API calls and stays fast

Execution Cache (cache.py)

Every tool execution is fingerprinted with a SHA-256 hash of tool_name + sorted(arguments) and stored in a local SQLite database (vault/cache/execution_cache.sqlite).

# Cache key generation def _generate_hash(tool_name, kwargs): dict_str = json.dumps(kwargs, sort_keys=True) combined = f"{tool_name}::{dict_str}" return hashlib.sha256(combined.encode()).hexdigest()

Cache Rules:

  • Tools can opt out by setting cacheable = False (used by live data tools like vision_map_analyzer, aemet_fire_risk, aemet_warnings)
  • Error results are never cached — only successful {"status": "success"} payloads
  • Cache is INSERT OR REPLACE — re-running the same query updates the cached value

Performance Optimizations

Optimization Description
Lazy Tool Imports Tools are only imported when first used — startup time is near-instant
Geometry Column Stripping CSV reader auto-excludes WKT/GeoJSON blobs (geometry, geom, wkt, etc.) to save tokens
Row Capping CSV reader limits results to 500 rows by default; csv_aggregate processes ALL rows server-side
Catalog Trimming VaultCatalogTool filters out massive legacy CSVs and strips Google Drive metadata to minimize token footprint
Async HTTP The FastAPI endpoint wraps the synchronous agent cycle in run_in_threadpool() so the event loop stays non-blocking
CSV field_size_limit Set to 2^31 - 1 to handle CSVs with enormous WKT geometry fields without crashing

The Skills System

Domain-specific expertise injected into the LLM context on demand

What Are Skills?

Skills are Markdown files in backend/skills/ that contain domain-specific instructions for the Planner LLM. They act as expert playbooks — teaching the LLM how to handle complex, multi-step scenarios that require domain knowledge.

Current Skills (4)

Skill Purpose
api_guidance.md Rules for correctly calling AEMET and SISCOVA APIs, handling two-step data URLs, fallback strategies
csv_cross_reference.md Patterns for chaining CSV reads and cross-referencing local data with live API results
data_routing.md Decision trees for routing queries to the correct data source (vault vs. API vs. Drive)
emergency_protocols.md PELSISCAV emergency response protocols and how to present seismic risk assessments

How Skill Injection Works

# 1. Discover all skills (reads YAML frontmatter only — cheap I/O) all_skills = discover_skills() # 2. Keyword-match against user prompt (no LLM call needed) selected = select_relevant_skills(prompt, all_skills) # 3. Inject ONLY matched skill bodies into the LLM system prompt skills_section = "=== SKILL: {name} ===\n{body}" for each selected skill
Why not just put everything in the prompt? Token economy. Each skill can be 2,000+ tokens. With 4 skills, that's 8,000+ tokens wasted on every query. By only injecting relevant skills, the Planner context stays lean and focused, reducing cost and latency.

Limitations & Future Work

Honest assessment of current constraints and improvement opportunities

Current Limitations

Limitation Detail Impact
No Streaming The agent waits for the entire pipeline (Plan → Execute → Synthesize) before returning. The user sees no intermediate progress. High perceived latency on complex multi-tool queries (5-30 seconds)
No Conversation Memory Each POST /api/chat is stateless — the agent has no memory of prior turns. Cannot handle follow-up questions like "now compare that with last month"
Sequential Execution Tools run one at a time. Independent steps (e.g., two AEMET calls) could run in parallel but don't. Slower than necessary for independent multi-tool plans
No Self-Correction Loop If a tool fails or returns unexpected data, the Orchestrator logs the error but cannot re-plan or retry with different arguments. Fragile on ambiguous queries where the first plan might be suboptimal
Cache Without TTL The SQLite cache has no time-to-live (TTL). Cached weather data could be served stale indefinitely. Mitigated by cacheable=False on live tools, but some tools cache when they shouldn't
Vision Limited to Gemini Multimodal analysis requires Gemini — if the Gemini API key is exhausted, vision analysis is unavailable. No fallback for image understanding tasks
Regional Scope Prompts, skills, and data sources are hardcoded for the Comunitat Valenciana. Expanding to other regions requires new tools and data sources. By design — this is a specialized agent, not a general-purpose one
Neo4j & Supabase Disconnected The .env template scaffolds Neo4j and Supabase integrations, but the code does not actively use them. Knowledge graph queries are not yet operational

Future Improvements

  • Server-Sent Events (SSE) for streaming intermediate results to the frontend
  • Conversation memory with a sliding context window or summary-based compression
  • ReAct-style self-correction: If a tool fails, re-invoke the Planner with the error context
  • Parallel tool execution with a dependency DAG instead of linear sequencing
  • Cache TTL with configurable expiry per tool category
  • Neo4j Knowledge Graph for entity-relationship queries across datasets

Anticipated Technical Q&A

Common questions professors may ask and their answers

Q: "Why not use LangChain's built-in AgentExecutor or tool framework?"

The system was designed from scratch to have full control over the execution pipeline. LangChain's AgentExecutor is a black box — it internally manages retries, token budgets, and tool selection in ways that are hard to debug or customize. Our custom Planner → Orchestrator → Synthesizer architecture allows: independent testing of each phase, explicit caching logic, custom placeholder resolution, and domain-specific skills injection. This also avoids the heavy dependency tree of LangChain.

Q: "How do you handle prompt injection / security?"

Three layers: (1) Google Drive sandbox — file access is restricted to a single authorized folder, verified by tracing parent IDs up to 5 levels; (2) Tool schema validation — the LLM can only call tools from the registered tool map with typed parameters; (3) Step cap — maximum 6 steps per plan prevents infinite loops. However, the Synthesizer does inject raw tool outputs into its prompt, which is a known surface for indirect prompt injection.

Q: "What happens when all LLM providers fail?"

After exhausting 3 retry rounds across all configured providers (up to 9+ individual model attempts), the LLMClient raises an exception that propagates to the FastAPI error handler, which returns a 500 Internal Server Error with a descriptive message. The system is designed to degrade gracefully — if only Gemini is down, HF or Ollama can handle text-only queries.

Q: "Why SQLite for caching instead of Redis?"

Simplicity and zero-dependency deployment. SQLite requires no external server, is ACID-compliant, and is file-based — perfect for a single-server application. Redis would be appropriate if the system were scaled horizontally across multiple worker processes, but for a single FastAPI instance, SQLite is optimal.

Q: "How does the system handle ambiguous queries?"

The Planner uses Chain-of-Thought reasoning (<thinking> blocks) to decompose ambiguous queries before generating the plan. The general tool acts as a catch-all for conversational queries (greetings, clarifications) that don't need data tools. If the Planner returns an empty plan, the system defaults to a single general step.

Q: "Why is the Planner temperature 0.1 and the Synthesizer 0.3?"

The Planner needs deterministic, structured JSON output — high temperature would introduce randomness in tool selection and argument generation. The Synthesizer benefits from slightly higher creativity to produce natural, well-formatted prose, but 0.3 is still low enough to avoid hallucination.

Q: "How scalable is this architecture?"

Vertically — a single server can handle moderate traffic since each query is processed in a thread pool. For horizontal scaling, the stateless architecture (no session state, no in-process memory) means multiple instances could be load-balanced. The SQLite cache would need to be replaced with a shared store (Redis/PostgreSQL) in that scenario.

Q: "What is RAG and how does this system implement it?"

Retrieval-Augmented Generation supplements an LLM's knowledge with external data retrieved at query time. This system implements RAG through: (1) structured retrieval via CSV queries, API calls, and Google Drive reads — the Planner decides what to retrieve; (2) semantic retrieval via Pinecone vector search over PDF chunks with Gemini embeddings; (3) augmented generation — the Synthesizer receives all retrieved data and generates a grounded response. Unlike simple RAG (query → retrieve → generate), this is agentic RAG where the LLM itself decides what, when, and how to retrieve.
